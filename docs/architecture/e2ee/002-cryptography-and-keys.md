# ADR-002: Cryptography and Key Hierarchy

Status: **Accepted primitives; web/Node prototype passing, React Native validation pending**

## Principles

- Do not implement cryptographic primitives.
- Use an audited provider with explicit cross-platform test vectors.
- Separate authentication credentials from vault encryption secrets.
- Generate data-encryption keys randomly; never derive note keys directly from a password.
- Version every algorithm, KDF parameter set, envelope, and payload schema.
- Treat decryption failure as terminal for that record; never return partial plaintext.

## Preferred suite

| Purpose | Primitive |
| --- | --- |
| Record encryption | XChaCha20-Poly1305, 256-bit key, 192-bit random nonce |
| Password KDF | Argon2id with per-wrapper 128-bit salt and stored parameters |
| Device signature | Ed25519 |
| Device key transport | Libsodium sealed box to the recipient X25519 key, plus an Ed25519-signed outer authorization envelope |
| Key derivation | HKDF-SHA256 with domain-separated labels |
| Locator | Keyed BLAKE2b-256 (`crypto_generichash`) |
| Randomness | Platform CSPRNG only |

The initial provider pair is `libsodium-wrappers-sumo` for web/Node and `react-native-libsodium` for React Native. Both expose the required libsodium operations. The checked-in `tests/vectors/e2ee-v1.json` fixture is the compatibility gate; the React Native implementation is not accepted until it passes those exact vectors. The sealed-box fixture is an open/decrypt vector because sealed encryption is intentionally randomized.

If XChaCha cannot be implemented safely and consistently on all target platforms, AES-256-GCM through a native/WebCrypto provider is an acceptable alternative only after nonce management and test-vector review. A suite change creates a new `suiteId`; it must not silently reinterpret old records.

## Key hierarchy

```text
Recovery Secret (random, offline)
        │ wraps
Passphrase KEK (Argon2id) ── wraps ──┐
Device-local wrapping key ─── wraps ─┤
                                     ▼
                            Vault Root Key (VRK)
                              │
                              ├── wraps Content Key epoch N
                              ├── derives Locator Key
                              └── wraps attachment DEKs
```

### Vault Root Key

- 32 random bytes generated by the first trusted client.
- Never uploaded in plaintext.
- Not used directly to encrypt note operations.
- Rewrapped on passphrase change; content does not need re-encryption.

### Content key epochs

- One active 32-byte content key encrypts new records.
- Old epochs remain available for decryption.
- Rotation creates a new epoch; it does not mutate historical records immediately.
- A revoked device that copied an old key can still read historical ciphertext it retained. Rotation only protects future epochs.

### Attachment data-encryption keys

- Each attachment receives a random 32-byte DEK.
- The DEK is wrapped by the active content key with vault/blob/epoch-bound AAD.
- Each chunk uses an independent random XChaCha20-Poly1305 nonce and binds vault ID, blob ID, epoch, chunk index, total count, and plaintext length as AAD.
- The encrypted manifest contains private filename/media type, total plaintext size, plaintext digest, and ordered encrypted-chunk hashes. Completeness is verified before materialization.
- Plaintext hashes are never used as server-visible IDs.

## Passphrase wrapper

The passphrase derives a Key Encryption Key, not a content key.

The implemented canonical wrapper stores `protocolVersion`, `wrapperVersion`, `suiteId`, `vaultId`, `kdfAlgorithm`, 128-bit salt, operations limit, memory limit, 192-bit nonce, and ciphertext. All metadata is authenticated as XChaCha20-Poly1305 AAD, and the encrypted payload repeats its vault/version context.

Version 1 uses Argon2id13 with a baseline of 64 MiB and two operations. Decoders reject weaker settings and cap attacker-controlled settings at 1 GiB and ten operations before derivation to prevent resource-amplification attacks. Production parameters remain stored per wrapper so later clients can upgrade them after device benchmarking. Passphrases are NFKC-normalized and limited to 1024 UTF-8 bytes before derivation.

Authentication password and vault passphrase are separate protocol concepts. They may share a UX flow, but the server must not receive the vault passphrase or a directly reusable vault derivation output.

## Recovery wrapper

- Recovery secret is exactly 256 random bits from the platform CSPRNG.
- Human format is `GIR1` plus Crockford Base32 and a domain-separated 40-bit BLAKE2b checksum; the checked-in vector fixes the cross-platform representation.
- The secret derives a vault-bound wrapping key through domain-separated keyed BLAKE2b-256. It is not password-based, so no slow KDF is needed for its full-entropy input.
- The VRK is wrapped with XChaCha20-Poly1305; vault/version/nonce metadata is canonical AAD and repeated inside the encrypted payload.
- Store the printable code offline and optionally as QR. The server stores only the encrypted wrapper.
- Recovery regenerates device wrappers; it does not change historical content keys unless the user rotates them.

## Record envelope

Binary canonical encoding uses RFC 8949 deterministic CBOR via `cborg`; JSON string concatenation is forbidden for signatures or AAD. The decoder accepts only Giraffle's restricted canonical subset and verifies canonicality by re-encoding.

```ts
interface EncryptedEnvelopeV1 {
  protocolVersion: 1;
  suiteId: "xchacha20poly1305-v1";
  schemaVersion: number;
  keyEpoch: number;
  nonce: Uint8Array;
  ciphertext: Uint8Array;
}
```

Authenticated Additional Data binds ciphertext to its context:

```text
protocolVersion
suiteId
vaultId
recordId
objectLocator
deviceId
deviceSequence
schemaVersion
keyEpoch
```

Moving ciphertext to another record, object, account, epoch, or schema must fail authentication.

## Key storage

- Device private keys and local DB wrapping keys live in iOS Keychain / Android Keystore through a small secure-storage wrapper.
- Large payloads never go into SecureStore.
- A biometric prompt gates access to a device wrapper; biometrics are not a KDF.
- Root/content keys should spend the minimum practical time in JavaScript memory.
- Keys, plaintext, nonces with associated context, and decrypted errors must never enter logs, crash reports, analytics, or Redux/devtools state.

## Crypto agility

Clients must preserve old decryptors while data using an old supported suite exists. Migration is:

1. decrypt with old suite
2. validate schema
3. encrypt a new record/checkpoint with the new suite and epoch
4. verify on another client
5. retire old ciphertext after retention and acknowledgement gates
